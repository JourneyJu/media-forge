# 日志规范

日志目标是定位问题、审计关键操作和观测成本，不是保存业务内容。

## 基本要求

- 使用结构化日志，避免只输出拼接字符串。
- 每条请求链路尽量携带 `requestId` 或 `traceId`。
- 多租户或用户相关日志需要携带 `tenantId`、`userId`、`workspaceId` 中可用的上下文。
- 异步任务日志需要携带 `jobId`、任务类型和状态。

## 日志级别

- `debug`：本地排查或低频详细上下文，生产默认可关闭。
- `info`：关键业务动作成功，例如创建工作区、上传完成、生成版本完成。
- `warn`：可恢复异常、降级、外部服务重试、配额接近上限。
- `error`：请求失败、任务失败、数据不一致、外部服务不可用。

## 禁止记录

- API Key、token、数据库密码、对象存储密钥。
- 完整用户隐私数据。
- 完整敏感 prompt、模型供应商凭据、系统 prompt 私密规则。
- 上传文件原始二进制内容。

## AI 调用日志

AI 调用必须记录模型供应商、模型名、调用场景、token 用量、耗时、结果状态和错误分类。

不记录完整 prompt；如需追溯，保存脱敏后的 prompt 快照 key，并在 PostgreSQL 中记录快照元数据。

## 上传与导出日志

- 上传日志记录文件类型、大小、对象 key、归属工作区、识别状态。
- 导出日志记录导出类型、文章版本、快照 key、耗时和失败原因。
- 对象 key 不能作为权限判断依据，只能作为定位对象的元数据。

## 错误上下文

- 错误日志需要包含稳定错误码和必要业务上下文。
- 捕获第三方错误时，不直接输出完整响应体；先做脱敏和截断。
- 同类错误连续出现时，需要能按 code、模块、供应商或任务类型聚合。
