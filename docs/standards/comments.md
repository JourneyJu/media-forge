# 注释规范

注释用于解释“为什么”和“边界”，不是复述代码。

## 应该写注释

- 业务规则不直观，且来自客户习惯、平台限制或历史决策。
- 有意选择了看起来不常规的实现，需要说明取舍。
- 存在兼容性、幂等、并发、缓存、事务或安全边界。
- AI prompt、排版 skill、导出 renderer 等规则可能被后续误改。
- 公共导出函数、复杂类型或跨服务契约不够自解释。

## 不应该写注释

- 不解释语法和显而易见的赋值。
- 不保留大段注释掉的旧代码。
- 不写没有负责人和条件的长期 TODO。
- 不在注释里保存密钥、真实用户数据、完整敏感 prompt。
- 不用注释掩盖命名差或函数过长的问题。

## 语言

- 文档注释和业务规则说明优先使用中文。
- 与第三方 SDK、协议字段、错误码强相关的注释可以使用英文术语。
- 用户可见文案不写在注释里，应进入常量、配置或文案资源。

## TODO

临时 TODO 必须包含原因、触发条件和后续处理方式。

```ts
// TODO: 等待微信复制兼容性测试后，移除 legacy style fallback。
```

禁止只写：

```ts
// TODO: optimize
```
