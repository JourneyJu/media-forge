# 通用开发规范

本规范适用于仓库内所有代码、脚本和工程配置。服务自己的细则可以更严格，但不能放宽本规范。

## 基本原则

- 先读 `AGENTS.md`、相关目录 `AGENTS.md`、`.workflow/` 和被改模块文档，再修改代码。
- 每个任务先声明需求分级、影响范围、`allowed_files` 和验证方式。
- 保持最小充分改动，不做顺手重构，不改无关文件。
- 涉及 API、schema、架构、安全、上传、AI 调用链路、数据迁移时，先同步契约和文档，再实现。
- 业务事实以 PostgreSQL 为准；对象存储只保存文件、快照、导出物和不可直接编辑的对象。
- 不把外部 PRD 原文作为仓库事实源；只把确认后的结论拆到架构、模块、API、测试和 ADR。

## 分层与边界

- 前端只调用后端 API，不直连 PostgreSQL、MinIO、Redis 或模型供应商。
- 后端 HTTP 入口保持薄层，只做参数解析、鉴权上下文注入、响应映射。
- 业务规则放在 service / policy；外部系统访问放 adapter / repository。
- 共享领域类型、请求响应类型、枚举和错误码优先来自 `packages/contracts`。
- 禁止在前端、后端分别手写同一份业务类型。

## 命名

- 代码标识符、接口字段、数据库字段使用英文。
- 文档、页面文案、用户可见错误信息默认使用中文。
- TypeScript 文件名使用 kebab-case 或项目既有命名；类、类型、接口使用 PascalCase；函数和变量使用 camelCase。
- 数据库表和字段使用 snake_case。
- 命名必须表达业务语义，避免 `data`、`item`、`temp` 这类无上下文名称长期存在。

## 依赖

- 不新增生产依赖，除非先说明原因、替代方案、体积或运维影响，并获得确认。
- 优先使用项目已有工具链和标准库能力。
- 新增依赖必须明确归属到具体 workspace，不能随意加到根包。
- 禁止为了绕过类型、测试或 lint 引入工具。

## 配置

- 配置通过环境变量或配置模块注入，不在代码中硬编码密钥、URL、桶名、模型 Key。
- `.env.example` 只放示例值，不放真实凭据。
- 服务启动必须能在缺少关键配置时给出可读错误，而不是运行到半路失败。

## 错误处理

- 错误要能区分用户输入错误、权限错误、业务状态冲突、外部服务失败和系统内部错误。
- 不吞异常；需要降级时必须记录原因和可观察上下文。
- 返回给用户的错误信息不要泄露内部路径、SQL、密钥、prompt 或模型供应商细节。

## 验证

- 小改动跑最小充分验证。
- 共享契约、公共逻辑、API、schema、上传、导出、AI 编排变更需要扩展验证范围。
- 测试失败时按 `.workflow/coding-flow.md` 分流，不直接改测试来迎合错误实现。
