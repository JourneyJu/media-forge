# ADR 009：用户生成与模型调用分离计量

## 状态

Accepted

## 日期

2026-07-30

## 背景

MediaForge 的一次用户生成请求可能经过多个 Agent 步骤，并产生多个模型调用和重试。如果直接把模型调用次数作为用户生成次数，会高估用户使用频率；如果只记录 Run，又无法准确表示实际供应商调用、重试 Token 和模型切换后的消耗。

监控需要同时回答：

- 每个用户发起了多少次生成；
- 每个用户消耗了多少 Token；
- 每个模型总体被调用多少次、消耗多少 Token；
- 单个用户在不同模型上的消耗。

用量数据未来可能用于成本分析，因此必须可追溯、幂等并且不依赖 Redis。

## 决策

使用两类 PostgreSQL 原始事实：

- `generation_usage_events`：一条记录代表一次被系统接受并持久化的用户生成请求。
- `model_usage_logs`：一条记录代表一次真实供应商调用 attempt。

生成事件以 `generation_id` 唯一，内部步骤和模型重试不增加生成次数。

模型调用以 `call_id` 和 `generation_id + step_id + attempt_no` 去重。每次真实重试独立计量，因为它可能产生实际 Token 和供应商成本。

Token 只采用供应商返回值。供应商未返回时标记 `unavailable`，不自行估算。

## 写入决策

Run、dispatch outbox 和生成事件在同一个事务中创建。

模型调用前必须先创建 `running` 用量日志。创建失败时不发送供应商请求，避免产生无法计量的调用。调用结束后在 `finally` 更新状态、Token 和耗时。

超过阈值仍为 `running` 的记录通过幂等对账修复。无法恢复的 Token 保持 unavailable，不根据内容估算。

Redis 只可用于任务调度和短期通知，不作为用量事实源。

## 查询决策

第一阶段直接对原始表执行 PostgreSQL 聚合：

- 支持 7 天、30 天和最长 180 天范围；
- 按用户、模型、路由、状态和日期建立索引；
- 数据存 UTC，按 `Asia/Shanghai` 分桶展示。

当数据规模或查询延迟需要优化时，再增加可重建的日汇总：

```text
usage_daily_user_stats
usage_daily_user_model_stats
usage_daily_model_stats
```

不单独维护系统总量事实，总量由用户和模型原始事实聚合。

## 隐私决策

用量事实只保存身份、关联 ID、模型快照、Token、耗时、状态和安全错误码。

不得保存：

- prompt；
- 文章、图片或用户输入内容；
- 模型原始输出；
- API Key、Authorization header 或加密凭据；
- 完整供应商请求和响应。

监控页面和 API 只允许 `admin` 使用。

## 备选方案

### 只从 Run 和 Step 聚合

优点：

- 不增加用量事实表。
- 实现较少。

缺点：

- Step 不一定与真实供应商 attempt 一一对应。
- 重试 Token、Token 缺失和路由快照难以准确表达。
- 未来 Step schema 变化会破坏历史统计。

结论：拒绝。Run/Step 用于执行事实，用量表用于计量事实，两者通过 ID 关联和对账。

### 只记录模型调用

优点：

- 一张表即可统计 Token 和模型调用。

缺点：

- 无法准确统计用户主动生成次数。
- 多 Agent 和重试会造成生成次数虚高。
- 模型调用前失败的生成会完全丢失。

结论：拒绝。

### 第一阶段直接建立日汇总

优点：

- 仪表盘查询更快。
- 原始表增长影响较小。

缺点：

- 增加汇总任务、补算、迟到数据和一致性修复。
- 当前数据量尚未证明需要。

结论：暂缓。第一阶段实时聚合，日汇总保持为可演进方案。

### Token 本地估算

优点：

- 供应商未返回 usage 时仍有数值。

缺点：

- 不同模型 tokenizer 不同。
- 多模态输入难以准确估算。
- 估算值可能被误当成真实成本。

结论：拒绝。缺失时明确标记 unavailable。

## 保留策略

日汇总未实现前，不自动删除原始事实。

日汇总实现并验证可重建后：

- 原始模型调用目标保留 180 天；
- 日汇总目标保留 24 个月；
- 审计记录使用独立安全保留策略。

清理必须分批、可暂停、可重试，避免长事务和表锁。

## 后果

正向影响：

- 用户生成次数不会受 Agent 数量和重试影响。
- Token 能按用户、模型、路由和实际 attempt 追踪。
- 模型切换和配置归档后仍可解释历史用量。
- 原始事实可用于对账和重建日汇总。

负向影响：

- 每次模型调用增加一次创建和一次终结写入。
- 用量写入失败会阻止供应商调用，降低部分可用性但避免不可计量成本。
- 第一阶段原始表会持续增长，需要索引监控和后续汇总。
- Token unavailable 会使总量明确不完整，页面必须展示缺失调用数。

## 与模型配置的关系

每条模型调用日志关联 `model_config_id` 和 `route_key`。模型配置第一阶段只禁用或归档，不物理删除，以保持历史用量外键和统计解释能力。

连接测试和模型能力验证属于管理操作，不进入生产用量统计。
