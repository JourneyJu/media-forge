# ADR-002：公众号生成采用可持久化 Agent 状态机和有界审阅循环

## 状态

Proposed

## 日期

2026-07-26

## 背景

单次模型调用容易产生结构松散、素材未参与排版、正文不足和修改不可追踪等问题。公众号生成需要先理解素材和制定计划，再依次完成排版、扩充、审阅和重构。部分方向选择必须由用户确认，长任务还需要支持刷新页面后继续、失败重试和版本恢复。

## 决策

由 `apps/service` 内的 Agent Orchestrator 管理可持久化状态机。模型负责生成结构化计划、骨架、正文和审阅报告，但无权自行推进状态、决定无限循环或直接覆盖当前文章版本。

执行顺序为：

```text
素材理解 → 计划 → 用户确认（可选）→ 排版骨架 → 内容扩充
→ 审阅 → 局部修订或结构重构 → 再扩充 → 终审 → 渲染
```

采用以下约束：

1. `layout` 与 `expanding` 分离；内容 Agent 不得自行改变章节结构。
2. 审阅输出结构化 `ReviewReport`，由 policy 决定 revise、restructure、waiting_user 或 complete。
3. 局部修订最多 2 次、结构重构最多 2 次、总步骤最多 12 步。
4. 连续两次评分没有提升或重构范围超过 30% 时暂停等待用户。
5. PostgreSQL 保存运行、步骤和用户决定；Redis 只保存队列、锁和短期进度。
6. 每个内容变化步骤保存文章版本，步骤使用幂等键。
7. 前端只展示计划、执行摘要和审阅依据，不展示模型原始思维链。

## 备选方案

### 一次模型调用生成完整文章

- 优点：实现简单、耗时和成本低。
- 缺点：素材和结构控制弱，无法稳定审阅、回退和用户介入。
- 结论：保留为本地演示或快速模式，不作为正式 Agent 模式。

### 让模型自行决定循环

- 优点：编排代码较少。
- 缺点：不可预测、可能无限循环、成本失控，且难以恢复。
- 结论：拒绝，循环由确定性 policy 控制。

### 只在前端保存执行过程

- 优点：后端数据模型简单。
- 缺点：刷新即丢失，无法可靠重试、审计和跨设备继续。
- 结论：拒绝。

### 展示完整模型思维链

- 优点：表面上更透明。
- 缺点：包含不稳定内部推理，可能泄露 prompt、素材隐私和安全信息。
- 结论：拒绝，只展示结构化计划、结论和依据摘要。

## 后果

- 新增 `agent_runs`、`agent_steps`、`agent_decisions` 和相应迁移。
- 新增 Agent API、共享契约、队列 Worker、确认 policy 和步骤事件。
- 模型调用次数和成本增加，需要记录每一步 token、耗时和失败。
- 用户可以观察、暂停、确认、取消和恢复生成过程。
- 自动循环可控，失败不会破坏已保存的最佳文章版本。
