# ADR 006：独立认证服务与 RBAC 权限模型

## 状态

Proposed

## 日期

2026-07-30

## 背景

MediaForge 已具备基础创作链路，后续需要控制台、用户管理、配额、模型配置和审计能力。现有实现仍以本地假用户为主，无法支撑多租户、管理员、跨资源权限校验和安全审计。

认证和权限会影响所有业务 API、对象归属、控制台写操作和成本控制。如果继续散落在 `apps/service` 内部，容易把业务逻辑、登录凭证和管理权限耦合在一起。

## 决策

新增独立 `apps/auth` 服务，负责用户、租户、成员、角色、权限、登录会话、token 和认证审计。`apps/service` 只消费 `AuthContext` 并执行业务资源归属校验。

第一阶段：

- 只支持账号密码登录。
- 使用 Argon2id 保存密码哈希。
- 默认 bootstrap 一个 `admin` 账户和 `owner` 角色。
- 生产环境初始密码必须由 `AUTH_BOOTSTRAP_ADMIN_PASSWORD` 提供。
- access token 使用非对称签名，业务服务通过 JWKS 验签。
- refresh token 使用高熵随机值，数据库只保存 hash，并启用轮换。
- 权限模型使用内置 RBAC：`owner`、`admin`、`editor`、`viewer`。

## 备选方案

### 继续在 `apps/service` 内实现认证

优点：实现更快，部署更少。

缺点：认证、权限、业务 API 和控制台配置耦合，后续拆分成本高；密码和 token 管理容易污染业务模块。

结论：拒绝。当前已经明确需要控制台和权限底座，独立边界更稳。

### 直接接入第三方 IAM / SaaS Auth

优点：安全能力成熟，减少自研。

缺点：会引入新外部依赖和供应商绑定；当前项目需要本地可控开发和较小范围账号密码登录。

结论：暂缓。后续可以在 `apps/auth` 内增加企业 SSO 或外部 IdP 适配。

### 自研复杂 ABAC / 策略语言

优点：表达力强。

缺点：第一阶段复杂度过高，测试和审计成本大。

结论：拒绝。第一阶段使用 RBAC + 资源归属校验。

## 后果

- 新增服务边界，需要部署、健康检查和配置管理。
- 数据库需要新增认证和权限相关表。
- `apps/service` 必须替换本地假用户，所有业务查询逐步接入 `tenantId` 和 `userId`。
- 控制台、配额和模型配置后续可以复用同一权限底座。
- 默认 `admin` bootstrap 成为高风险路径，必须强制改密并禁止硬编码生产密码。
