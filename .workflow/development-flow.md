# MediaForge 开发流程

本流程参考 VibeCodingProject / LOGOS 的开发方式，并结合 MediaForge 的公众号内容生成业务落地。

## 核心原则

1. 契约优先：共享类型、Schema 和 API 契约先于实现。
2. 文件边界：每个任务改代码前必须声明 `allowed_files`。
3. 测试门禁：验证通过，或失败分流说明清楚，才允许进入完成报告。
4. 人工签字：范围、风险、schema、依赖、反复失败必须人工确认。
5. 快照安全：生成文章版本必须保存可复现的历史快照。
6. Loop 显式化：文档自审不通过回到文档修改；测试不通过回到 Coding；方案问题回到人工确认。

## 需求分级

拿到需求后先分级，动手前说明结果。判断不了时，往大一级走。

| 级别 | 判断标准 | 流程 |
| --- | --- | --- |
| S 小改动 | 不改接口契约、不改 schema、不改架构、不影响核心流程，且能在单模块内完成 | 说明分级理由 → 直接做 → 跑最小充分验证 → 完成说明 |
| M 中改动 | 涉及接口变更、用户可见行为、数据写入、鉴权权限、模型调用链路，但不改服务边界和主架构 | 只读分析 → 方案 + AI 自审 → 等人工确认 → 确认后实现 |
| L 大改动 | 新增/变更服务边界、改 schema、改主链路、引入新外部依赖或数据迁移 | 只读分析或临时 spike → 在 `.plan/` 创建计划 → PRD/架构/契约/schema/测试方案 + AI 自审 → 等人工确认 → 确认后实现 |

开工前输出：

```text
需求分级：S / M / L
分级理由：
影响面：
是否需要人工确认：是 / 否
下一步：
```

## 人工确认闸门

以下变更必须先停在方案确认点：

| 触发项 | 最低级别 | 要求 |
| --- | --- | --- |
| 新增或修改 API | M | 先同步契约和影响面 |
| 修改请求/响应字段 | M | 先同步契约和兼容性说明 |
| 修改错误码 | M | 先同步错误码文档 |
| 前后端联调新能力 | M | 先说明前端、服务、契约影响面 |
| 登录、鉴权、权限 | M | 先说明安全影响和验证方案 |
| 数据写入、删除、上传 | M | 先说明数据归属、异常路径和验证方案 |
| AI 调用链路变化 | M | 先说明编排、模型、prompt、成本影响 |
| 数据库 schema 或迁移 | L | 先更新 schema、数据库文档和迁移/回滚方案 |
| 服务边界变化 | L | 先更新架构文档和 ADR |
| 新外部依赖 | L | 先说明替代方案、引入理由和风险 |

## L 级计划规则

识别为 L 级改动时，必须先在 `.plan/` 创建计划文件。没有 `.plan` 计划和人工确认，不得进入正式实现。

L 级计划必须包含：

- 需求背景和 L 级分级理由。
- 非目标。
- 影响面。
- 推荐方案。
- 契约与数据变更。
- `allowed_files` 草案。
- 实施步骤。
- 验证方案。
- 迁移与回滚。
- 风险与应对。
- AI 自审。
- 人工确认记录。

计划文件命名规则：

```text
.plan/YYYYMMDD-short-title.md
```

使用模板：

```text
.plan/plan-template.md
```

L 级计划完成前，只允许：

- 只读分析。
- 临时 spike。
- 更新计划文档。
- 更新必要的外部需求拆解结论、架构说明或 ADR 草稿。

如果实现中发现影响面扩大，必须回到 `.plan/` 更新计划并重新人工确认。

## 设计流

```text
需求进入
→ 需求分流
→ 文档更新
→ AI 自审
→ 人工确认
```

### 需求进入

记录以下信息：

- 用户问题。
- 目标用户。
- 产品界面。
- 涉及数据。
- AI 行为。
- 导出、上传或存储影响。

### 需求分流

把需求拆成小任务。单个任务通常不应修改超过 5 个文件。

每个任务必须包含：

- 目标。
- 验收标准。
- 验证命令。
- `allowed_files`。
- 回滚或失败处理方式。

### 文档更新

实现前更新相关文档：

- 外部 PRD 变化：不落 PRD 原文，拆解到架构、模块、API、测试和 ADR。
- 功能决策：更新 spec。
- L 级计划：更新 `.plan/`。
- 架构变化：更新 `docs/architecture/`，并按架构路由同步模块文档。
- 模块变化：更新 `docs/modules/{module}/README.md`。
- 接口或数据形状：更新 contracts。
- API 变化：更新 `docs/api/{module}.md`。
- 测试范围变化：更新 `docs/testing/plans/{module}.md` 和 `docs/testing/cases/{module}.md`。
- 架构决策：更新 ADR。

### 文档分级路由

文档落地按下面顺序判断：

```text
外部 PRD / 需求文档 → 拆解为仓库内长期事实
架构边界 → docs/architecture → docs/modules
模块职责 → docs/modules
接口契约 → packages/contracts + docs/api
测试策略 → docs/testing/plans
测试用例 → docs/testing/cases
长期决策 → docs/adr
运行排障 → docs/runbooks
```

如果涉及架构文档改动，并且影响具体模块，必须继续路由到模块目录。模块文档更新后，根据模块内容同时补充 API 文档、测试方案和测试用例文档。

PRD 不作为仓库文档资源。不要把 PRD 原文复制到仓库，也不要在仓库内维护 PRD 版本。仓库只保存从 PRD 拆解出来的架构、模块、接口、测试和 ADR。

### AI 自审

M/L 级需求提交人工确认前，必须先自审。自审不是复述方案，要主动挑毛病。

自审至少覆盖：

- 分级复核。
- 服务边界。
- 契约与数据。
- 异常路径。
- 安全风险。
- 测试方案。
- 反方意见。

自审输出：

```text
AI 自审结论：通过 / 不通过 / 信息不足
分级复核：
服务边界：
契约与数据：
异常路径：
安全风险：
测试方案：
反方意见：
需要人工重点看的问题：
```

### 文档 Loop

文档自审不通过时，必须回到文档修改，不进入实现。

```text
文档撰写 / 更新
→ AI 自审
→ 自审通过？
  → 是：进入人工确认或 Coding
  → 否：回到文档修改
  → 信息不足：暂停，一次性提出关键问题
```

文档 Loop 的停止条件：

- AI 自审结论为通过。
- 或信息不足，需要用户补充。
- 或发现属于 L 级，转入 `.plan/`。

## 实施流

```text
锁定 allowed_files
→ 编码实现
→ 运行测试
→ 测试通过？
  → 是：实施报告
  → 否：Coding Loop
→ 人工评审
→ 完成
```

详细 Coding 流程见 `.workflow/coding-flow.md`。

### 锁定 `allowed_files`

改代码前先写任务边界：

```yaml
task: 新增工作区列表 API
allowed_files:
  - packages/contracts/src/workspaces.ts
  - apps/service/src/workspaces/*
  - apps/service/test/workspaces/*
verification:
  - pnpm --filter @mediaforge/service test
```

如果必须修改其他文件，先更新任务边界。

### 编码实现

实现必须遵守：

- 只改声明范围内的文件。
- 优先使用既有契约和 Schema。
- 有真实风险的行为要补测试。
- 不静默格式化无关文件。

### 运行测试

先跑最小充分验证，再按风险扩大范围：

```bash
pnpm --filter @mediaforge/contracts typecheck
pnpm --filter @mediaforge/service test
pnpm --filter @mediaforge/web test
pnpm typecheck
pnpm lint
```

### Coding Loop

测试失败时：

```text
实现问题 → 回到编码实现
测试用例问题 → 修正测试并说明原因
契约问题 → 回到 contracts 和文档同步
方案问题 → 停止编码，回到方案或 .plan，等待人工确认
环境问题 → 记录未验证项，不算通过
同类失败 3 次 → 停止，输出失败报告，等待人工介入
```

失败报告必须包含：

- 失败命令。
- 错误摘要。
- 初步原因。
- 下一步建议。

## 完成标准

任务完成时必须说明：

1. 改动摘要。
2. 关键文件。
3. 设计取舍。
4. 验证结果。
5. 未验证项或风险。
6. 是否需要更新 `CONTEXT.md`、ADR、架构、模块、API、测试或 standards。
